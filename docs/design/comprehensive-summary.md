## 一、故障排查篇

### 1.1 排查方法论：调用链分析法

```
遇到 500 错误
    │
    ├─ ① 看终端日志 → 找到 Traceback 最后一行
    │
    ├─ ② 定位报错文件和行号
    │
    ├─ ③ 分析调用链（谁调了谁，传了什么参数）
    │       ┌────────────────────────┐
    │       │ detect_image()         │
    │       │   → _run_detect(str)   │  ← 字符串路径
    │       │     → infer(img_input) │
    │       │       → cache.get(img) │
    │       │         → image.shape  │  ← 崩溃！str 没有 shape
    │       └────────────────────────┘
    │
    └─ ④ 修复 + 验证
```

**核心思想**：不要只看错误本身，要看**数据在调用链中经历了什么变换**。

### 1.2 本次遇到的故障清单

| 故障 | 根因 | 排查手段 | 修复 |
|------|------|---------|------|
| FAISS UnicodeError | C++库不支持中文路径 | `grep` 搜索代码中的硬编码路径 | 项目移到 E 盘 |
| 端口被占用 (Errno 10048) | 旧进程未正常关闭 | `netstat -ano \| findstr :8000` | `taskkill` 杀进程 |
| 检测接口报 500 (AttributeError) | 字符串传入需要 numpy 的函数 | 分析调用链，对比两个路由的传参 | 用 `isinstance` 区分类型 |
| CLAHE 导致检测精度下降 | 图像增强改变了模型训练时的特征分布 | 查看 `preprocess()` 源码 | 绕过推理引擎，走原始 YOLO 路径 |
| 备选项重复 | 合并逻辑未做语义去重 | 查看前端展示 → 分析合并代码 | 用 `set` 实现名称去重 |
| 服务重启导致前端请求失败 | 模型加载空窗期无进程监听 | 理解 TCP 连接原理 | 规范操作流程 + 健康检查 |
| JS 语法错误导致按钮失效 | 编辑时误删函数声明，产生孤儿代码 | 浏览器报 `(pageError)` → 逐段检查 | 恢复被误删的 `showImagePreview` 函数 |

### 1.3 排查工具体系

```powershell
# 1. 看后端日志
e:/post-detect-master/.venv/Scripts/python.exe -m uvicorn backend.main:app --host 0.0.0.0 --port 8000

# 2. 直接加载模块（绕过 uvicorn，快速验证）
e:/post-detect-master/.venv/Scripts/python.exe -c "import backend.main; print('OK')"

# 3. 测试 API 接口（命令行）
python -c "import requests; r=requests.get('http://localhost:8000/weather/current?lat=30&lng=120'); print(r.json())"

# 4. 检查端口占用
netstat -ano | findstr :8000

# 5. 检查模型文件
Get-Item "backend/models/best.pt" | Select-Object Length, LastWriteTime
```

### 1.4 排查思维原则

> **原则一：不要猜，要看日志。** 90% 的问题在终端日志的最后一行就有答案。
>
> **原则二：对比法。** 同样功能的两个接口（detect_image vs detect_base64），一个报错一个正常，对比传参差异就能定位。
>
> **原则三：最小复现。** 用一行 Python 命令复现问题，比在浏览器里反复操作效率高十倍。
>
> **原则四：改一处，想想会影响哪三处。** 每次代码修改都可能引入副作用——去重引入了新 bug，进度条引入了语法错误，欢迎消息引入了逻辑冲突。

## 二、效果设计篇

### 2.1 字体系统设计（面向农户）

**挑战**：农户普遍年龄偏大，字体小了看不清；但字体太大又显得不专业。

**解决方案**：建立 CSS 变量体系，统一管理字号。

```css
:root {
  --font-xs: 13px;    /* 次要信息 */
  --font-sm: 14px;    /* 辅助说明 */
  --font-base: 16px;  /* ✅ 正文主体 */
  --font-lg: 18px;    /* 害虫名称、按钮 */
  --font-xl: 20px;    /* 标题 */
  --line-relaxed: 1.7; /* 宽松行高 */
}
```

**设计决策**：
- 正文 16px + 行高 1.7 = 每行约 27px，阅读舒适
- `--text-sub` 颜色加深，提高对比度
- 输入框字体同步放大，方便农户输入

### 2.2 色彩系统

| 元素 | 颜色 | 设计意图 |
|------|------|---------|
| 用户消息 | 蓝色 `#0671AD` | 科技感、专业 |
| AI 回复 | 淡绿 `#eaf7ee` | 温暖、自然，与农业主题呼应 |
| 系统提示 | 渐变绿 | 区分于普通消息 |
| 湖南元素 | 红色 `#c0392b` | 辣椒红，地域文化符号 |

### 2.3 进度条设计演化

```
v1（简单）: 三个弹跳点 + "正在思考"
    ↓ 用户反馈：太单调
v2（动画）: 无限循环流动条
    ↓ 用户反馈：走完了回答还没来，假完成感
v3（专业）: 对数衰减曲线 + 真实数据跳满 ✅
    p(t) = 0.88 × (1 - e^(-t/3.5))
```

**设计决策**：进度条永不自己到 100%，等真实数据到达才跳满。这是 YouTube、Google Drive 等大厂采用的模式。

### 2.4 交互设计决策

| 决策 | 方案 | 思考过程 |
|------|------|---------|
| 欢迎消息 | 纯文字引导，不放功能按钮 | 避免与原有上传按钮功能冲突，保持职责单一 |
| 零接触快捷操作 | 检测卡片底部放 3 个预设问题 | "看得到但不强制点"，保留用户自主权 |
| 交错入场 | 每行延迟 0.08s 依次滑入 | 45° 角递进，形成"逐条审视"的节奏感 |
| 不确定检测 | 置信度 ≥ 75% 不显示备选项 | 高分不纠结，低分才列可能 |

## 三、企业与学业联系思维篇

### 3.1 什么是"企业级思维"？

```
学生思维                         企业思维
──────                           ──────
"能跑就行"                      "还要考虑异常情况"
"遇到 Bug 就慌"                 "Bug 是信息，不是灾难"
"改一处看一处"                  "改一处想三处"
"功能做完就行"                  "还要考虑用户体验"
"用户会按我的预期操作"          "用户会乱点"
"代码是我的作品"                "代码是要交接的资产"
```

### 3.2 本次的思维跃迁实例

**实例 1：检测精度问题**

```
学生阶段："模型不准 → 调参数试试"
企业阶段："Precision vs Recall 是 trade-off，需要根据业务场景确定侧重点"
           ↓
    展示场景下 Precision 更重要（宁可漏检，不可误报）
           ↓
    引入"类别自适应阈值"——不同害虫不同标准
```

**实例 2：进度条设计**

```
学生阶段："做个动画让它转起来"
企业阶段："这个加载时长的分布是什么？P50/P95/P99 分别是多少？"
           ↓
    "用户能接受的等待极限是几秒？我先快后慢，大厂都这么干"
           ↓
    "真实数据到了才跳满，不到 100% — 这是诚实的进度条"
```

**实例 3：合并检测逻辑**

```
学生阶段："把所有重叠框都列出来"
企业阶段："3 种可能还是 5 种可能，对用户来说有区别吗？"
           ↓
    "同名的去掉，高分的不显示备选 — 信息越少，决策越快"
```

### 3.3 从"做功能"到"做产品"的追问清单

每次做一个功能前，问自己这五个问题：

```
① 用户是谁？（年龄、文化水平、使用场景）
   → 我的用户是农户 → 字体要大、操作要简单

② 用户在这个步骤会想什么？
   → 检测出害虫后，他第一反应是"怎么治"→ 放快捷按钮

③ 出了问题怎么办？
   → 网络断了 → 静默降级，不弹错误框
   → 模型不准 → "请拍微距特写"引导，而不是列低分结果

④ 这个功能和已有功能冲突吗？
   → 欢迎消息的按钮和原有上传按钮 → 冲突了 → 去掉欢迎消息按钮

⑤ 用户明天还会用吗？
   → 没有历史记录 → 加了 localStorage 可以留存
   → 没有登录 → 识别用户身份的入口
```

### 3.4 企业级项目的特征

| 特征 | 你的项目做到了吗 | 可以怎么加强 |
|------|----------------|------------|
| **优雅降级** | ✅ 定位失败不报错 | 可以增加更多降级场景 |
| **可观测性** | ⚠️ 有终端日志 | 可以加结构化日志 + 错误追踪 |
| **防御性编程** | ✅ `isinstance` 类型判断 | 可以加参数校验装饰器 |
| **用户体验闭环** | ✅ 检测→问答→天气 | 可以加历史记录形成数据闭环 |
| **代码可维护性** | ⚠️ 模块化尚可 | 可以加类型注解 + 单元测试 |

## 四、数学原理在 UI 中的应用

### 4.1 对数衰减曲线（进度条）

$$p(t) = 0.88 \times (1 - e^{ -t / 3.5 })$$

```
用途：让进度条"先快后慢"，永不自己到 100%
应用：问答加载进度、文件上传进度等不确定时长的操作
```

### 4.2 相位偏移（加载动画）

```
原理：三个点用不同的 animation-delay 错开启动时间
效果：形成"波浪式"弹跳，人眼感知为"正在处理"
应用：加载中提示、数据刷新动画
```

### 4.3 阻尼振荡（按钮交互）

```
transform: scale(1) → scale(0.97) → scale(1)
用 cubic-bezier(.4, 0, .2, 1) 模拟物理回弹
应用：按钮点击反馈、通知徽章弹跳
```

### 4.4 交错入场（列表展示）

$$delay(n) = n \times 0.08s$$

```
让列表项依次出现，形成"逐条审视"的节奏感
如果改用指数公式 delay(n) = 0.03 × n²，前面快后面慢，视觉更自然
```

## 五、项目管理思维

### 5.1 变更管理

```
需求提出 → 可行性评估 → 优先级排序 → 最小化实现 → 验证 → 记录文档
                                                         ↓
                                                  本次改动的副作用
                                                  （去重bug、语法错误等）
```

### 5.2 优先级矩阵

```
                 高价值
                   │
    P2 批量对比    │  P0 修复崩溃
      数据库       │   字体优化
                   │   进度条
                   │
  ────────────────┼──────────────── 易实现
                   │
    P3 离线功能    │  P1 快捷按钮
      暗黑模式     │   欢迎消息
                   │   交错动画
                   │
                 低价值
```

### 5.3 技术债务记录

| 债务 | 说明 | 建议偿还时机 |
|------|------|------------|
| 模型精度 mAP 49.4% | 训练数据或模型架构问题 | 下一轮迭代 |
| 无用户认证 | 数据孤岛，换设备丢失 | 启动数据库时 |
| 前端无框架 | 纯 HTML+JS，难以维护 | 功能稳定后考虑 Vue/React |
| 无自动化测试 | 改代码全靠手动测试 | 核心接口稳定后 |
